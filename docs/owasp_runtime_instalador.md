# Seguridad previa: runtime SQLite del instalador

**Superficie nueva:** sí: descargas de herramientas e intérprete, ejecución de binarios y archivos bajo el directorio del usuario. Se evalúa antes de implementar; la revisión independiente y las pruebas por plataforma siguen pendientes.

- A01: directorio privado por usuario; no escritura en rutas de otros usuarios. Verificar permisos y no aceptar rutas escapadas. La protección ACL nativa de Windows requiere verificación en Windows.
- A02: `uv` de versión y hashes fijados; Python gestionado con catálogo de distribución del propio `uv` y TLS. Las huellas no protegen frente a un artefacto legítimo malicioso; documentar procedencia.
- A03: `subprocess` con argumentos separados, sin shell; rutas calculadas internamente y salida de intérprete validada.
- A04: descargas y comprobaciones con timeout; errores detienen la instalación y no configuran MCP con un runtime no verificado. No tocar base ni sidecars como parte de la preparación del runtime.
- A05: comprobar versión SQLite y FTS5 con el intérprete efectivo; no desactivar guardián. Mantener entornos de datos y configuraciones previos si preparación falla.
- A06: herramienta `uv` fijada por versión y hashes; CPython gestionado fijado por versión, distribuido por python-build-standalone. Actualizar explícitamente versiones y hashes.
- A07: no hay IPC ni autenticación nueva.
- A08: instalación bajo ruta de usuario, publicación y comprobación antes de configurar agentes; no sustituir el Python global, base ni WAL. Verificar entorno heredado para no permitir mirrors de descarga arbitrarios.
- A09: informar fallos sin incluir datos de recuerdos ni secretos; nunca mostrar éxito cuando el runtime falla.
- A10: fuentes de descarga controladas por `pip` aislado y catálogo de `uv`, sin URL de usuario ni mirrors heredados. No deshabilitar TLS.

**Límites:** la instalación no cambia procesos ya vivos ni escritores externos; éstos deben usar un runtime corregido antes de escribir en WAL. No prueba Windows o macOS sin ejecución real. `pip install -r requirements.txt` no ejecuta el instalador y no queda cubierto automáticamente por este cambio. No resuelve WAL ajeno ni recuperación.

## Evidencia histórica de la preparación

- En la primera etapa, `install.py` contenía el sondeo de SQLite/FTS5 y dos piezas aún no conectadas: descarga de CPython con `uv` y construcción de una generación con `venv`. La integración posterior se documenta más abajo.
- `uv` 0.13.7 se obtiene en directorio temporal con `pip --require-hashes`, hashes de ruedas publicados por PyPI y sin instalarlo globalmente. La versión de CPython solicitada es 3.13.18. La revisión del código fuente de `uv` 0.13.7 (`crates/uv-python-managed/src/downloads.rs`, `extract_reader`) confirmó que comprueba SHA-256 **cuando el catálogo lo contiene**; los registros ordinarios 3.13.18 del catálogo incluido traen hash. Sigue pendiente verificar plataforma y variante realmente seleccionadas en una instalación real.
- En este sandbox se descargó e instaló `uv` en temporal y se intentó descargar CPython, pero el destino de la redirección de GitHub, `objects.githubusercontent.com`, no está entre los hosts permitidos: falla el handshake TLS. No se desactivó TLS. Tampoco se probó la entrega real de CPython en Windows o macOS.
- En Linux se creó un entorno real con el `requirements.txt` completo: **175 MiB** según `du -sh`, sin base ni corpus WordNet, reutilizando Python del sistema. Para esa medición se simuló el resultado de la comprobación: el SQLite real era **3.40.1**, por lo que **no** es un entorno seguro ni demuestra el tamaño del CPython privado descargado. NumPy instalado: 2.4.6. Python privado, corpus y generaciones antiguas sumarían espacio; memoria RAM y disco son medidas distintas.
- En ausencia de pip en el Python inicial, la descarga de `uv` actual falla de manera cerrada; falta un bootstrap aislado verificado que no modifique el Python global. El `venv` requiere soporte de `venv`/`ensurepip` en el Python base.
- Falta integrar preparación y publicación en el flujo principal, enrutar MCP y sistema/SSE, comprobar instalaciones existentes, acordar actualización concurrente sin borrar entornos en uso y cubrir puntos de entrada pip. `pip install -r` por sí solo no ejecuta un bootstrap. Antes de activar, verificar también que el proceso real use el mismo SQLite que el sondeo: variables como `LD_LIBRARY_PATH` pueden alterar bibliotecas al arrancar, y el sondeo las elimina. En Windows falta revisar ACL y políticas de rutas de DLL. No presentar la preparación como completa mientras falten estas comprobaciones.
- Se añadió a CI una prueba opt-in de descarga y entorno reales en Linux, Windows y macOS; no toca la base de usuario. Está pendiente de ejecución y sus resultados, no se asume éxito.
- Ejecución GitHub Actions `43141683456`, commit `cfb5b56`: los tres trabajos de portabilidad Linux, Windows y macOS terminaron en éxito, incluyendo la prueba de descarga real de CPython, verificación efectiva de SQLite/FTS5 y creación de un entorno con las dependencias. Las dos suites completas de Python 3.11 y 3.12 seguían en ejecución al registrar esta evidencia. Esto no prueba todavía el flujo de instalación integrado, SSE ni procesos existentes.
- Se aisló además la configuración global de pip con `PIP_CONFIG_FILE=os.devnull`; `--isolated` por sí solo no ignora necesariamente archivos globales. El índice de instalación se fija a PyPI. Prueba local con archivo global simulado y prueba focal: **81 passed, 1 skipped, 2 xfailed**. El skip es la descarga real en el sandbox restringido; los dos xfail son las regresiones WAL conocidas.

### Ampliación previa: bootstrap sin pip del sistema

Se evalúa obtener la rueda de `uv` directamente de la API HTTPS de PyPI cuando falte pip, y extraer solo el ejecutable a un directorio temporal privado. A01/A08: no escribe en el Python global y solo extrae un miembro fijo; A02/A06: acepta exclusivamente hashes previamente fijados; A03/A10: URL HTTPS y host oficiales, sin shell; A04: límites de tamaño y tiempo; A05: plataformas no reconocidas fallan sin activar nada; A07: sin autenticación nueva; A09: errores visibles sin datos de memoria. La metadata solo ayuda a localizar la rueda: su hash publicado por la red no sustituye el hash fijado localmente. Redirecciones y tamaños deben validarse, y las pruebas de plataformas reales deben repetirse.

- Implementado fallback temporal sin pip global: selección explícita de rueda, límite de descarga y extracción de un único ejecutable solo tras comprobar SHA-256 fijado; solo permite PyPI y files.pythonhosted.org y rechaza redirecciones a otros hosts. La prueba local real Linux descargó y ejecutó `uv 0.13.7`; pruebas con versiones simuladas: 18 aprobadas, 1 omitida (descarga integral limitada por red). Se añadió prueba real a CI para Windows y macOS. El instalador principal aún no llama estas piezas.

### Ampliación previa: publicación y actualizaciones del entorno

Una generación nueva se prepara sin borrar ni alterar la anterior y solo se publica después de comprobar el intérprete y dependencias. A01/A08: directorio por instalación y usuario, rechazo de rutas o symlinks fuera de la raíz, marcador temporal y reemplazo atómico; A02/A06: versiones y hashes fijados, actualización por nueva generación; A03: sin shell y rutas validadas; A04/A05: fallo deja el marcador previo, no abre la base; A07: sin autenticación nueva; A09: reporte de fallo sin datos de recuerdos; A10: reutiliza las fuentes aprobadas. No se eliminarán automáticamente generaciones antiguas: procesos existentes pueden estar usándolas y falta una política verificable de limpieza. Publicar un marcador no reinicia ni cambia los procesos vivos.

### Ampliación previa: integración del instalador

Se propone usar una raíz privada por usuario e instalación identificada por un hash de la ruta del proyecto; se rechazan enlaces y permisos inseguros y solo se publican generaciones comprobadas. MCP estándar y OpenCode deben comparar también el intérprete para actualizar configuraciones antiguas. Si preparar dependencias falla, la configuración anterior se conserva. Se revalida el marcador al usarlo. Los procesos existentes no cambian solos: debe advertirse que hay que reiniciarlos; clientes externos no quedan bajo control del instalador. La ejecución de `--systemd` debe usar el mismo intérprete. No se considera que `pip install -r` ni instalar un paquete por sí solos ejecuten este flujo; esa integración sigue sin implementarse y no se afirma cobertura. La ruta Windows hereda ACL del perfil del usuario; la comprobación independiente de ACL sigue pendiente antes de afirmar privacidad contra otros usuarios en Windows.

### Ampliación previa: servicio SSE

El servicio actual escribe en `/etc` con sudo y usa `tempfile.mktemp`; se sustituirá para nuevas configuraciones por un servicio de usuario con archivo temporal seguro y reemplazo atómico. A01/A08: sin escritura privilegiada ni `mktemp`; A03: argumentos del archivo systemd escapados, sin shell, sin interpolar el usuario desde el entorno; A04/A09: si systemd falla se informa; A05: usa el intérprete seleccionado; A06/A07/A10: no añade descargas ni credenciales; A02: no manipula secretos. No detiene ni sobrescribe un servicio de sistema previo: su administrador debe reiniciarlo o retirarlo para evitar una instancia antigua o un conflicto de puerto. El servicio de usuario depende de que systemd de usuario esté disponible.
- La prueba real del bootstrap sin pip en macOS falló en GitHub Actions `43144587862` porque el Python inicial reporta plataforma `universal2`; Linux y Windows aprobaron. Se corrigió la selección para elegir el binario por arquitectura activa en `universal2` y se agregaron pruebas unitarias para ARM e Intel. La corrección requiere nueva ejecución real; no se asume que haya pasado todavía.

### Integración y base versionada

El flujo principal ahora prepara el entorno privado antes de configurar MCP, y `--show-config`/`--systemd` exigen la generación publicada. La actualización de runtime no modifica generaciones previas; hay que reiniciar procesos vivos. Se retiró el `git pull` y la copia de solo `.db` del camino de reinstalación sobre un repositorio existente: un pull podría reemplazar una DB versionada mientras sigue abierta y una copia sin WAL no es una copia consistente. Se conserva el código local y no se hace actualización automática de código por ese camino; esta limitación debe resolverse aparte sin comprometer los datos. No se ejecutó el instalador sobre la DB real. La prueba de instalación integrada usa una DB centinela temporal y se ejecutará en CI.
- La primera prueba integrada de CI (`6eef2ea`) pasó en Linux y macOS, pero Windows falló por un `UnicodeEncodeError` al imprimir iconos en una consola cp1252. Se sustituyeron los iconos de terminal por símbolos ASCII y se agregó una prueba con salida cp1252; requiere confirmar de nuevo en Windows.
- Una ejecución focal registró 99 aprobadas, 3 omitidas, 2 xfail y una falla en `test_el_hash_reutilizado_no_sobrevive_a_cambios_del_archivo`: la prueba escribe ceros en la última página y la huella no cambió. Al ejecutar esa prueba sola pasó; se conserva el resultado y no se atribuye automáticamente al instalador ni se declara resuelto.

### Verificación sin abrir la base del usuario

La verificación anterior del instalador ejecutaba la CLI `estado` y lanzaba el servidor MCP; ambos pueden abrir la DB y causar actividad de SQLite. Se sustituye en este flujo por una comprobación de importaciones y del SQLite/FTS5 en memoria: A01/A08 evita acceso y cambios al par DB/WAL; A03 usa argumentos separados y código fijo, sin shell; A04/A05 aborta si faltan dependencias, antes de publicar/configurar; A09 comunica error; A02/A06/A07/A10 no introduce fuentes, credenciales ni descargas. La comprobación no equivale a probar la comunicación con un agente real ni a una revisión de los datos.

### Comprobación de la integración

En el commit `1c0b1ac`, los trabajos de portabilidad de GitHub Actions `43146010966` aprobaron en Linux, Windows y macOS, incluyendo descarga real, dependencias, publicación y actualización de una configuración MCP de prueba con una base centinela temporal intacta. La comprobación del sondeo se hace con variables del cargador saneadas; el entorno final de un cliente externo puede ser distinto, por lo que la política SQLite en el proceso real sigue siendo necesaria. La privacidad de ACL de Windows y la limpieza segura de generaciones antiguas no están verificadas. No se han cambiado ni copiado archivos de la DB real.

## Evaluación adicional: instalación por pip sin ejecutar un segundo comando

Se examinó `pysqlite3==0.6.2` como una posible alternativa instalable directamente por pip. En Linux x86_64 / Python 3.11, su rueda contiene SQLite **3.54.1** y FTS5 trigram funciona en memoria; el SQLite del mismo Python estándar es **3.40.1**. Es una observación aislada y no significa que BioRAG ya lo use.

La rueda publicada para CPython 3.11 cubre macOS ARM, Linux x86_64 y Windows x86/x64, pero no macOS Intel, Linux ARM ni Windows ARM; el sdist disponible no garantiza por sí mismo un SQLite corregido. Además, `pysqlite3` y `sqlite3` tienen clases de excepción y conexión distintas; un `backup()` entre sus conexiones falla con `TypeError`, y la rueda probada no tiene `blobopen`, `serialize` ni `deserialize`. BioRAG usa `sqlite3` en múltiples capas y clientes: sustituir solo algunas supondría mezclar drivers, políticas y escritores. No se cambia el backend ni el guardián sin un diseño y pruebas completos por plataforma. Una instalación `pip install -r requirements.txt` normal solo instala las dependencias declaradas: no llama a `install.py` ni configura MCP; depender de efectos secundarios de construcción de paquetes para lanzar un instalador sería inseguro y no fiable. La instalación actual del entorno privado sigue requiriendo `python install.py` desde el repositorio.
