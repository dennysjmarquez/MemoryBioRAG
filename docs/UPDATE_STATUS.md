# Installed update and database status

BioRAG tracks two separate facts:

- Code availability is determined by the update channel: DEV compares Git commits; STABLE compares `VERSION` with the publicly recommended, non-blocked tag and verifies that tag exists.
- Database readiness is local. `biorag update --dry-run` opens the resolved database read-only, compares the replaceable `data` key `biorag_applied_update_id` with the installed commit SHA, checks the core schema generated by the normal initializer in an isolated `:memory:` database, and runs SQLite quick and foreign-key checks.

The `data` key is written or replaced only after the lifecycle migration and schema verification succeed. It is not a per-release history and does not use the human-facing semantic version. If there is no code commit to fetch but the key is absent/stale or a required core table/column is missing, `--dry-run` reports that the database lifecycle is unconfirmed; a normal `biorag update` still performs the backup, lifecycle and verification.

## Applying an update

`biorag update` (or `python -m core.updater --channel stable`) applies by default; `--dry-run` is the optional preview. Before changing files, it stops only the daemon whose PID BioRAG registered and whose executable, working directory, and owner are verified. It then takes the exclusive OS database lease, creates and tests a backup, fast-forwards code, installs the project's dependencies, runs the lifecycle in a fresh process, verifies the schema, SQLite integrity and applied update ID, and writes a machine-readable receipt. Other programs are not scanned or stopped; BioRAG's shared/exclusive database lease coordinates all managed clients. The external MCP host is not controlled by the updater and should reconnect after the update to load new code.

The lease is cross-process: POSIX uses `flock`; Windows uses `LockFileEx` with shared locks for clients and an exclusive maintenance lock. Every managed SQLite connection must use `core.database_access.connect` to participate. Programs that bypass BioRAG and open SQLite directly do not honor the lease. The updater does not scan or stop arbitrary processes, and cannot guarantee coordination with such external SQLite clients; this is a technical boundary, not something the user should troubleshoot from process IDs. It never kills an unknown or unrelated process.

A stopped BioRAG daemon is relaunched only after lifecycle and database verification succeed. On any update failure, the updater attempts to restore the prior Git revision, reinstall its dependencies, restore the verified database snapshot atomically, and clear the update barrier only if rollback succeeds. It compares installed package names/versions with a pre-update inventory; if they differ or cannot be verified, rollback is marked incomplete. This is not a byte-for-byte snapshot of the Python environment, so the updater does not promise an “as if nothing happened” rollback. The receipt reports `rolled_back` only when the available checks pass; its backup is retained as evidence. If any rollback step fails, the receipt reports `recovery_required`, the safety barrier remains active, and the backup is preserved. Do not restart BioRAG in that state; contact support. After verified success, the temporary backup is removed. The external IDE/agent host is never stopped by the updater and should reconnect and verify the applied update ID.

MCP checks the stable release policy in the background and sends a notice before a later tool call. Its planning tool returns the CLI command but does not apply the update from inside the resident server. The agent must obtain explicit user authorization and invoke that command using the installation's Python environment. A matching update ID is not proof against a table deleted after the update; structural checks detect missing core schema objects. Optional components that create their own schema must register a verifier in the lifecycle.

The Git updater supports clean Git checkouts and fast-forward updates. Non-Git installs must use their original package manager and then run the lifecycle; the updater does not turn a wheel, archive or managed installation into a Git checkout.
