# Installed update and database status

BioRAG tracks two separate facts:

- Code availability is determined by the update channel: DEV compares Git commits; STABLE compares `VERSION` with the publicly recommended, non-blocked tag and verifies that tag exists.
- Database readiness is local. `biorag update --dry-run` opens the resolved database read-only, compares the replaceable `data` key `biorag_applied_update_id` with the installed commit SHA, checks the core schema generated by the normal initializer in an isolated `:memory:` database, and runs SQLite quick and foreign-key checks.

The `data` key is written or replaced only after the lifecycle migration and schema verification succeed. It is not a per-release history and does not use the human-facing semantic version. If there is no code commit to fetch but the key is absent/stale or a required core table/column is missing, the plan reports that the database lifecycle is unconfirmed; an authorized `--yes` run still performs the backup, lifecycle and verification.

## Applying an update

`biorag update --yes` (or `python -m core.updater --channel stable --yes`) is a separate CLI process. Before changing files, it inventories processes holding the selected database, its WAL/SHM files, or BioRAG's maintenance lease. It terminates only processes it can identify as BioRAG MCP, daemon, CLI, or worker and only when they hold this exact database. Unknown consumers or an incomplete process scan make the updater refuse before changing code. It then takes an exclusive OS database lease, creates and verifies a backup, fast-forwards code, installs the project's dependencies, runs the lifecycle in a fresh process, verifies the schema, SQLite integrity and applied update ID, and writes a machine-readable receipt.

The lease is cross-process: POSIX uses `flock`; Windows uses `LockFileEx` with shared locks for clients and an exclusive maintenance lock. Every managed SQLite connection must use `core.database_access.connect` to participate. Programs that bypass BioRAG and open SQLite directly do not honor the lease; process inspection can find visible open handles, but the updater cannot prove the absence of every uninspectable external consumer. In such a case it fails closed when the scan reports an access gap. It never kills an unknown or unrelated process.

A stopped BioRAG daemon is relaunched and startup is checked if the update reaches verified completion. The receipt separately records whether an MCP process was stopped, that restart is owned by the external IDE/agent host, and that host reconnection plus update-ID verification is still pending; the updater cannot claim an MCP health check it cannot perform. The agent should retry MCP health/version checks and ask to reopen the host/client if it did not reconnect. If code/dependency/lifecycle preparation fails, the receipt marks `recovery_required` and preserves the backup; code, dependencies and DB are not blindly reset. Use `python -m core.recovery --receipt <receipt> --stage` to stage separate recovery copies without overwriting the live DB.

MCP checks the stable release policy in the background and sends a notice before a later tool call. Its planning tool returns the CLI command but does not apply the update from inside the resident server. The agent must obtain explicit user authorization and invoke that command using the installation's Python environment. A matching update ID is not proof against a table deleted after the update; structural checks detect missing core schema objects. Optional components that create their own schema must register a verifier in the lifecycle.

The Git updater supports clean Git checkouts and fast-forward updates. Non-Git installs must use their original package manager and then run the lifecycle; the updater does not turn a wheel, archive or managed installation into a Git checkout.
